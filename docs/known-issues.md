# Известные проблемы и ограничения

- **Туннелирование шага в плоских зонах.** Где кривизна ровно ноль, оценка ошибки ≡ 0 и шаг растёт ×5 за шаг;
  стадии RK могут перепрыгнуть тонкий слой кривизны, и ошибка перестаёт зависеть от tol. Лечится только
  ограничением шага (`Shape.hcap`: расстояние до носителя кривизны + доля масштаба внутри). Любая новая сцена
  с плоскими зонами обязана задавать hcap. (Найдено на компактной червоточине, см. журнал 2026-10-23-01.)
- **Неустойчивые орбиты.** Лучи у L ≈ b (фотонная сфера на горловине Эллиса) экспоненциально чувствительны
  к начальным данным; это физика. Ставится потолок попыток шага `n_max`, такие пиксели красятся отдельным цветом
  (пурпурный) и учитываются в `frac_step_cap`. Тест отклонения исключает L ∈ (0.9, 1.1)·b. Они же дают
  максимальную ошибку направления в рендер-бенчмарке компактной червоточины (L ≈ 0.999·b, ADR-0002).
- **Большие α нестабильны.** α = 10/ℓ_s на компактной червоточине при tol = 1e-4 даёт NaN (ADR-0001).
- **JAX на Windows — только CPU.** Метрика сравнения методов — проходы SDF на луч, а не миллисекунды.
- **Фильтр кубмапы мипами** (M19) — главная ошибка режима A: 41–43 дБ против 50–56 дБ с точным гауссовым
  фильтром на сцене с тонкими линиями (docs/reports/stage-2.md). При анизотропии ≥ 8 и следах ≳ 0.3 рад малая ось
  перемывается (как аппаратный зажим анизотропии).
- **Jet15 дорог**: 18–28 скалярных SDF на CPU; режим A — 102 прохода Jet15 на пиксель.
- **Эталонный фильтр**: квадратура Гаусса–Эрмита малого порядка непригодна на следах ≳ 5 текселей — использовать
  плотную сетку (`cubemap.sample_gauss_exact`).
- **Детектор нелинейности** не проверен на сцене с каустиками в фоне.
- **Общий seed RNG** в тестах: не брать подсказки направлений из того же потока, что и точки фигуры
  (на S³ совпадают с нормалью).
- **GPU: занятость 17 %** при интегрировании с Якоби (252 регистра); фолбэк — 68 % кадра 1080p
  (docs/reports/stage-3.md). Вариант Якоби 2×2 не проверен.
- **Режим B: искры у червоточин.** Где источник виден только сквозь кривизну, NEE запрещена (правило задания) —
  свет находится лишь сэмплированием BSDF; шум убирают накопление и денойзер. У Эллиса плоских зон нет вовсе.
- **Режим B: денойзер через копии хост ↔ GPU** — обмен памятью Vulkan ↔ CUDA не сделан (ADR-0007).
- **Режим B: ε_hit = c_hit·w** задаёт допуск перескока шага: объекты тоньше ε_hit/2 на прямой могут быть пропущены.
- **GPU: кубмапа без рамки** полагается на бесшовную выборку Vulkan; отдельного теста по направлениям у рёбер нет.
- **Гладкая склейка M11 обрезана при q ≤ 1e-2** (хвост ≤ e⁻⁹⁹·W² отброшен); на нулевое множество и
  производные влияния нет на уровне float64.
- **Редактор сцен (DD-008).** Режим редактирования (динамические шейдеры) медленнее быстрого: 1080p, сцена 3 —
  52.3 / 16.2 мс против 37.1 / 14.5 мс (движение / покой); выход после структурной правки ждёт перегенерацию 11–18 с.
  Только формы ball4 / тор / полупространство и параметры имеющихся многообразий;
  отмены (undo) нет; не больше 32 объектов. Объект без «на M» после смены многообразия может оказаться вне M (не
  виден). Перегенерация вызывает Python через `std::system` — на Windows пути с не-ASCII символами в каталоге
  проекта/venv не проверены. Без `dynamicRendering` окно работает без панелей.
- **Режим A: пурпурный пиксель изредка (GPU, не понято).** На двух горловинах в 320×180 в ~10–40 % запусков одного и
  того же графа один-два пикселя режима A — пурпурные (`modea_shade`: `Status ≠ DONE_ESCAPE`). Это всегда пиксели
  8192 и/или 24576 (поток 0 групп 128 и 384, границы 32 КБ буфера `Status`). `pt_camera` проходит пиксель ровно
  один раз и пишет `DONE_ESCAPE` (2); `modea_detect` после `shade` видит 2; итоговый буфер — 2; только `modea_shade`
  читает 4. Хост до DD-010 (e5c943f) ведёт себя так же — не регрессия. Не помогли: отключение `VkPipelineCache`
  (`GEO4D_NO_PIPELINE_CACHE`), самый грубый барьер `ALL_COMMANDS`/`MEMORY_*` между диспетчеризациями, барьер в
  начале командного буфера, `globallycoherent` у `gStatus` в modea. Помогло (0 из 79): лишнее атомарное чтение
  `InterlockedOr(gStatus[i], 0)` в `modea_shade` — механизм не понят, в код не внесено. Двойного исполнения и
  перекрытия памяти нет (выделения отдельные). Воспроизведение — `prototype/scripts/repro_modea_status_race.py`;
  журнал 2026-10-25-02. Следствие: любой побитовый тест окна с числом пикселей > 8192 может изредка не пройти
  (`test_export_renders_same` поэтому идёт в 96×54).
