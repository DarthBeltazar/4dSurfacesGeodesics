# DD-005: Режим B — path tracing на гиперповерхности

## Контекст и задача
Этапы 1–3 дали интегратор геодезических (BS32, M2/M3/M7/M8), поля Якоби и режим A (только фон), порт на GPU
(Slang → Vulkan, float32, граф диспетчеризаций в хосте). Режим B добавляет объекты и освещение: однонаправленный
трассировщик путей по геодезическим M. Задание (TASK.md, этап 4):
- объекты — 4D SDF g, пересечённые с M; шаг ≤ g(x), уточнение по эрмитову сплайну;
- BSDF-сэмплирование, русская рулетка; NEE с MIS только при прямом соединении в той же плоской зоне;
  допуск интегратора растёт с глубиной; ray cones для мип-уровня;
- пиксели, чей первичный луч ушёл в фон, — режим A без шума;
- временное накопление при неподвижной камере, денойзер (OptiX на NVIDIA, иначе OIDN) с AOV альбедо и нормали;
- ориентиры 1080p: 1 сэмпл + денойзер — 40–100 мс; 64 сэмпла + денойзер — 3–5 с.

Что уже есть и переиспользуется: конвейер «только луч» (Jet7, 29–69 регистров), wavefront-граф хоста (`graph`:
косвенные диспетчеризации, циклы, компакция), кубмапы BC6H, режим A целиком (центральные лучи с Якоби,
детектор M20, фолбэк), сцены M11/M12 с аналитическим пролётом плоских зон.

## Цели / не-цели
**Цели.**
- Пересечение геодезической с объектами {g = 0} ∩ M с точностью, согласованной с допуском интегратора.
- Несмещённый трассировщик (проверка: печь, совпадение NEE+MIS с только-BSDF, сравнение с эталоном прототипа).
- Сцена 3 задания: две компактные червоточины (M12) + шары, тор, источники света.
- Режим A для фоновых пикселей, стохастика для пикселей объектов и «смешанных» (силуэт в следе пикселя).
- Денойзер с AOV, временное накопление, измерения 1080p/4K против ориентиров.

**Не-цели.**
- Двунаправленные методы, краевая задача для геодезических (запрещено заданием), NEE через кривизну.
- Преломляющие материалы (диэлектрики) — предлагается отложить, см. вопрос 4.
- Интерактивная камера и ролик — этап 5. Накопление — только при неподвижной камере.
- Volumetrics, поляризация, спектральный рендер.

## Математика
Новые формулы получат номера M26–M32 в `docs/math.md` **после** численной проверки в прототипе (правило задания).
Здесь — черновики.

**M26 (черн.). Объекты и ограничение шага.** Объект — 4D SDF gₖ: R⁴ → R, 1-липшицева (|∇gₖ| ≤ 1),
gₖ ≤ евклидова расстояния до {gₖ = 0}. Видимая поверхность — {gₖ = 0} ∩ M. Так как хорда в R⁴ не длиннее дуги
геодезической на M (|Δx| ≤ Δs), шаг Δs ≤ gₖ(x) не пересекает объект — тот же довод, что для маркеров M21.
- Объединение для ограничения шага: g = min по объектам — это не SDF геометрии, а управление шагом
  (не дифференцируется), жёсткий min здесь допустим. Если объединение нужно как геометрия — smin (≤ min,
  градиент — выпуклая комбинация, липшицевость ≤ 1 сохраняется). Материал — по argmin (дискретный выбор,
  не геометрия).
- Предел шага: h ≤ min(hcap(x), g(x) + ε_hit), т. е. шаг может «перескочить» поверхность не глубже ε_hit;
  пересечение обнаруживается сменой знака g между концами принятого шага. Объекты тоньше ε_hit могут быть
  пропущены (ε_hit ≪ размеров деталей).
- ε_hit = max(c_hit·w, 16·ulp(|x|)), w — ширина конуса луча (M31), c_hit ≈ 0.05 (подобрать измерением).
  Чистый sphere tracing без перескока на скользящих лучах сходится медленно; перескок с уточнением снимает это.
- Размещение: 4D-шар |p − c| − r с центром c на листе w = ±W плоской зоны режет лист по 3D-шару радиуса r.
  В кривой зоне пересечение — искажённое тело; это допустимо и нужно для теста (объект у горловины).

**M27 (черн.). Уточнение пересечения по эрмитову сплайну.** На принятом шаге [s₀, s₀ + h] известны (x₀, v₀) и
(x₁, v₁) (после проекции M3), dx/ds = v (дуговая параметризация). Кубический эрмитов сплайн
x(σ) = h₀₀(σ)x₀ + h₁₀(σ)h v₀ + h₀₁(σ)x₁ + h₁₁(σ)h v₁, σ ∈ [0, 1], точность O(h⁴) — порядок локальной ошибки BS32.
Корень g(x(σ)) = 0 — метод Иллинойса (регула фальси с модификацией), 3–5 скалярных вычислений g, затем
проекция точки на M (M3) и одна поправка Ньютона по касательной (вдоль v) до |g| < ε_hit. Направление в точке
попадания — эрмитова производная, спроецированная на T_xM и нормированная.

**M28 (черн.). Кадр оттенения на M.** Нормаль объекта в многообразии: n_g = P∇g / |P∇g|, P = I − nnᵀ (M14).
Ортонормированный базис T_xM: {n_g, t₁, t₂}, все ⊥ n (Грам–Шмидт координатных осей R⁴ в порядке, как в M17).
BSDF вычисляется в 3D-координатах этого базиса; исходящее направление ω = a·t₁ + b·t₂ + c·n_g касательно и
нормировано по построению (проверяется). Вырождение |P∇g| → 0 (поверхность объекта касается M по нормали) —
пометить пиксель и считать поглощение.

**M29 (черн.). Плоская зона и прямые соединения.** Плоская зона Z — открытое множество, где M совпадает
с гиперплоскостью (S ≡ 0, геодезические — прямые в R⁴). Для M11/M12: листы w = ±W вне шаров |q − cᵢ| < ρ₀.
Важно: K = 0 не достаточно (S¹×R² плоская внутренне, но геодезические в R⁴ не прямые) — нужно S ≡ 0.
Соединение x → y допустимо, если x, y в одной Z и отрезок [x, y] не пересекает ни одного шара кривизны
(аналитически) и ни одного объекта (sphere tracing по прямой, скалярный g). То же — для направления на
бесконечность (фон-источник, вопрос 3): луч x + t d, t ∈ [0, ∞), не пересекает шаров и объектов.
MIS (степенная эвристика, β = 2): вес BSDF-попадания в источник использует pdf NEE **только если** сегмент пути
целиком прошёл по прямой в Z без шаров кривизны — это ровно область, где существует NEE-стратегия, поэтому
веса согласованы. Путь к тому же источнику через кривизну (другой ω) получает вес 1.

**M30 (черн.). Допуск по глубине.** tol_d = min(tol_max, κ · max(θ_pix, γ_d)), γ_d — угловая ширина конуса
после d-го отскока (M31). Для первичного луча (d = 0, γ = θ_pix) это ADR-0002/ADR-0004. После диффузного
отскока γ велико, и tol упирается в tol_max (кандидат 1e-2; выбрать по развёртке смещения, см. план проверки).

**M31 (черн.). Конусы лучей.** Состояние (w, γ): w — ширина, γ — угол раствора. На сегменте w += γ·Δs
(кривизна M в эволюции конуса **не учитывается** для вторичных лучей — источник ошибки, измеряется).
Первичный конус: w₀ = 0, γ₀ = θ_pix; для первого попадания можно взять точную ширину из полей Якоби центрального
луча (п. 2 решения). На отскоке γ += γ_bsdf(шероховатость) (для GGX ≈ 2·α_GGX, для Ламберта — потолок π/2).
Выборка фона при уходе луча: мип-уровень lod = log₂(γ / θ_texel), θ_texel = π/(2N) для грани N×N,
`SampleLevel`. На бесконечности w/расстояние → 0, остаётся γ.

**M32 (черн.). Нормаль для денойзера.** Денойзеру нужна 3D-нормаль, согласованная между соседними пикселями.
Базис камеры (r, u) переносится параллельно вдоль первичного сегмента: dW/ds = −⟨Sv, W⟩ n, Sv = P(Hv)/|∇f|
(M15 при DW/ds = 0); на отражении базис отражается в T_xM. Нормаль в «экранных» координатах:
(n_g·r̃, n_g·ũ, −n_g·v). Hv берётся HVP-проходом (M23, w = v) вместо Jet7 на первичном сегменте.
Альтернатива — см. «Рассмотренные альтернативы».

## Предлагаемое решение

### 1. Сцена и объекты
- Объекты пишутся один раз против `IReal`/`ops` (как SDF M), но вычисляются в основном скалярно (шаг) и на
  Dual4/Jet7 (∇g в точке попадания). Набор: 4D-шар, «тор в листе» g = √((√(x²+y²) − R)² + z² + (w − w_c)²) − r
  (в листе — 3D-тор), полупространство-пол g = z − z₀ (не зависит от w ⇒ есть на обоих листах), smin-группы.
- Материал: Ламберт; GGX-металл (VNDF-сэмплирование); излучатель (радиантность L_e, двусторонний или
  односторонний). Альбедо — константа или процедурная клетка с фильтрацией по ширине конуса.
- Источники: излучающие объекты (любые — для BSDF-попаданий) и **NEE-источники** — 4D-шары с центром на листе
  целиком в плоской зоне (сэмплирование по телесному углу шара в 3D-координатах листа). Фон — кубмапа на лист.
- **Сцена 3 (предложение, вопрос 5).** M12: c₁,₂ = (∓4, 0, 0), b = 1, ρ₀ = 3, W = 1.5. Верхний лист: пол
  z = −3.5 (вне шаров кривизны, на обоих листах), диффузный шар r = 0.8 в (0, −4.5, 0), металлический тор R = 1.2,
  r = 0.3 в (0, 4.5, 0), сферический источник r = 0.5 в (0, 0, 4). Нижний лист: диффузный шар и источник другого
  цвета (видны сквозь горловины). Один малый шар внутри зоны кривизны у горловины c₁ (тест интегрирования
  с объектом). Камера — в плоской зоне верхнего листа.
- Дополнительные сцены для проверки: гиперплоскость + объекты (евклидов эталон), Эллис + объекты (нет плоских
  зон ⇒ только BSDF-сэмплирование), S³ + излучающий маркер (замкнутое пространство, фона нет).

### 2. Кадр: классификация пикселей и проход камеры
**Проход камеры** — существующий wavefront режима A (центральные лучи с Якоби), дополненный объектами:
- ограничение шага по g (M26) и регистрация попадания центрального луча;
- **флаг «смешанный»**: min по пути (g(x) − c_mix·r_fp(s)) < 0, где r_fp — радиус следа пикселя из полей Якоби
  (пиксельные поля × 3σ, плюс поля апертуры × радиус линзы — так учитывается и глубина резкости). Детектор M20
  по соседям не видит субпиксельных объектов — этот флаг их ловит.
- Классы: **фон** (центральный луч ушёл, флаг не поднят) → режим A без шума (с детектором и фолбэком как
  на этапе 3); **объект** (центральный луч попал) и **смешанный** → стохастика.
- При неподвижной камере проход камеры выполняется **один раз** и кэшируется; на каждый сэмпл — только
  стохастика. В интерактиве (1 spp) проход камеры — каждый кадр; фолбэк режима A там — с уменьшенным числом
  сэмплов (кандидат 8 вместо 64: шум гасит накопление/денойзер). Это главный рычаг бюджета (фолбэк = 27 мс
  кадра 1080p на этапе 3).
- Альтернатива (сравнить измерением): проход камеры «только луч» для классификации + Якоби только для фоновых
  пикселей.

### 3. Трассировщик (на пиксель класса «объект»/«смешанный», один путь на пиксель на проход)
1. Первичный луч: джиттер в пикселе (гауссов фильтр σ = 0.5 px, как в режиме A) + точка на линзе (M16).
2. **Продление**: в плоской зоне — прямая со sphere tracing по g (скалярно) до попадания / входа в шар кривизны
   (аналитически) / ухода на бесконечность (луч прошёл ограничивающие сферы всех объектов); в кривой зоне —
   BS32 «только луч» с пределом шага M26 и уточнением M27. Допуск — M30. Потолок n_max: путь обрывается,
   счётчик таких путей в отчёте (как неустойчивые орбиты).
3. **Оттенение** в точке попадания: L_e с весом MIS (M29); NEE (если точка в плоской зоне): выбор источника
   (пропорционально мощности), точка на нём, теневой луч — прямой отрезок; сэмплирование BSDF → новое
   направление в T_xM, обновление пропускания, конуса (M31), допуска (M30). Русская рулетка с глубины 3:
   p = clamp(max(пропускание), 0.05, 0.95). Максимальная глубина — 16 (страховка).
4. **Уход в фон**: L = кубмапа(лист, d∞) с lod по M31 и весом MIS для фона-источника (если вопрос 3 — да).
5. **Смещение от поверхности** после отскока и для теневых лучей: x₀ = proj_M(x_hit ± ε_off·n_g) (знак — по
   стороне ω), ε_off = max(1e-4·ℓ_s, 64·ulp(|x|)); требование g(x₀) > ε_hit, иначе удвоить ε_off (≤ 3 раз).
   Утечки света проверяются отдельным тестом.
6. AOV на первом недзеркальном попадании: альбедо, нормаль (M32). Для ушедших лучей — альбедо = цвет фона,
   нормаль = −направление (типичная договорённость денойзеров; уточнить по документации выбранного).

### 4. Wavefront и мегаядро
Как на этапе 3: сначала **мегаядро** (весь путь в одном потоке) — базовая версия для проверки и сравнения;
затем wavefront на графе хоста. Очереди:
`gen` (первичные лучи) → `extend_flat` (прямые, скалярный g) / `extend_curved` (BS32, Jet7) → `shade`
(материалы, NEE, BSDF, рулетка) → `shadow` (прямые отрезки) и `escape` (кубмапа) → снова `extend_*`.
Компакция — как в режиме A (префикс-сумма по subgroup + один atomic). Число итераций — калибровочным прогоном.
Разделение плоских и кривых сегментов в разные очереди убирает дивергенцию «дешёвый скалярный пролёт против
дорогого интегрирования».

### 5. Накопление и денойзер
- Накопление: running mean в RGBA32F по сэмплам (сброс при смене камеры/сцены); AOV усредняются так же.
- Денойзер — на всём кадре; затем пиксели класса «фон» **заменяются** точными значениями режима A
  (денойзер не портит фон; ореолы на границе классов — риск, измеряется).
- Выбор денойзера — вопрос 2. Факты (проверено 2026-10-24):

| | OptiX Denoiser | Intel OIDN 2.x |
|---|---|---|
| библиотека | `nvoptix.dll` уже в драйвере 610.88 | готовые сборки Windows с GPU-устройством CUDA (~57 МБ zip) |
| заголовки | `NVIDIA/optix-dev` (GitHub, 9.1.0); лицензия NVIDIA SDK — **без права распространять исходники**, в репозиторий не кладём, скачиваем при сборке | Apache-2.0, можно положить в `third_party/` |
| зависимость | `optix_host.h` включает `<cuda.h>` ⇒ нужен CUDA Toolkit (winget) или самописные объявления CUDA Driver API | нет (CUDA внутри библиотеки) |
| обмен с Vulkan | вручную: `VK_KHR_external_memory_win32` → `cuImportExternalMemory` + семафоры | встроенно: `oidnNewSharedBufferFromWin32Handle` (импорт памяти Vulkan) |
| задание | предписан для NVIDIA | запасной вариант |

  **Рекомендация:** OptiX, как предписано заданием, с установкой CUDA Toolkit (только заголовки и
  `cuda.lib`/динамическая загрузка `nvcuda.dll`); OIDN — запасной вариант, если обмен памятью окажется
  хрупким. Время обоих в 1080p/4K будет измерено; если OIDN не хуже по качеству/времени — предложу замену с цифрами.

### 6. Раскладка данных и память (под 8 ГБ)
Состояние пути (SoA): x, v (2 × float4), пропускание (float3), конус (w, γ), h, s, глубина/флаги/пиксель (uint ×2),
RNG (uint ×2), pdf последнего BSDF-сэмпла и флаг «сегмент прямой в Z» (для MIS), базис AOV r̃, ũ (2 × float4,
только до первого попадания) ≈ 112 Б. Теневая очередь ≈ 48 Б. Накопление: цвет + альбедо + нормаль RGBA32F = 48 Б.

| | 1080p (2.07 М) | 4K (8.29 М) |
|---|---|---|
| пути (112 Б) | 0.23 ГБ | 0.93 ГБ |
| тени (48 Б) | 0.10 ГБ | 0.40 ГБ |
| накопление и AOV (48 Б) | 0.10 ГБ | 0.40 ГБ |
| режим A (этап 3, буферы прохода камеры) | 0.51 ГБ | 2.0 ГБ (переиспользуются после прохода) |
| кубмапы BC6H | 0.06 ГБ | 0.06 ГБ |
| денойзер (рабочая память — измерить) | ? | ? |

Итого ≲ 1 ГБ (1080p) и ≲ 4 ГБ (4K) без денойзера — в бюджете 8 ГБ; при нехватке — тайлы.

### 7. Прототип (до GPU)
По правилу «формулу сначала в прототипе»: объекты и M26, уточнение M27, кадр M28, плоская зона и MIS M29,
перенос базиса M32 — в `prototype/geo4d/` (новые модули `objects.py`, `pathtrace.py`). Малый трассировщик путей
на CPU (JAX, 32²–64², до ~1000 spp) — эталон для GPU, как эталонный рендер режима A на этапе 2.

## Рассмотренные альтернативы и почему отвергнуты
- **Чистый sphere tracing без перескока** (h ≤ g, попадание при g < ε): медленно на скользящих лучах
  (классическая проблема) и не использует плотный вывод интегратора; эрмитово уточнение предписано заданием.
- **Плотный вывод BS32 вместо эрмитова сплайна** — тот же порядок, но требует хранить стадии; эрмит по концам
  шага дешевле и не зависит от метода (DOPRI5 опцией — ADR-0003).
- **NEE через кривую зону** (поиск геодезической между точками) — краевая задача, запрещена заданием.
- **Конусы с кривизной (скалярное уравнение Якоби для вторичных лучей)** — требует гессиана на каждой стадии
  (HVP/Jet15) для всех вторичных лучей; сначала измерить ошибку плоских конусов, усложнять только если она видна.
- **Нормаль для денойзера в объемлющих координатах** (xyz-часть n_g) — бесплатно, но вырождается, где n_g ≈ ±e_w
  (у горловин). **Базис из полей Якоби центрального луча** — без HVP на сэмплах, но для сэмплов, ушедших по
  другому пути (силуэт), базис неверен. Оставлены запасными: сравнить качество денойза с M32.
- **Денойзер только на пикселях объектов** — денойзеры работают на полном кадре; маскирование после — проще.
- **Отдельный трассировщик для фоновых пикселей** — противоречит заданию (фон — режим A без шума).

## Бюджет производительности и памяти (оценка → позже измерение)
Оценки на 4080 SUPER, 1080p, сцена 3 (компактные червоточины):
- Проход камеры (режим A с объектами): интегрирование ≈ 4–11 мс (этап 3: 4.0 мс компактная, 10.8 мс Эллис),
  фолбэк при 8 spp ≈ 3–4 мс (64 spp — 25–27 мс).
- Один сэмпл трассировщика: «только луч» дешевле канала Якоби (регистры 29–69 против 252 ⇒ занятость выше);
  оценка 2–4 мс на сегмент-кадр, ≈ 2.5 сегмента в среднем (рулетка, рост допуска) + тени/оттенение ≈ 2 мс
  ⇒ **≈ 7–12 мс на сэмпл**.
- Денойзер: OptiX ≈ 3–6 мс, OIDN ≈ 10–25 мс в 1080p (оценки по публичным данным, **измерить**).
- **1 spp + денойзер:** ≈ 4–11 + 3–4 + 7–12 + 3–25 ≈ **20–50 мс** (ориентир 40–100 мс).
- **64 spp + денойзер:** проход камеры с полным фолбэком 40 мс + 64 × (7–12) мс + денойзер ≈ **0.5–0.8 с**
  (ориентир 3–5 с) — запас на более дорогие сцены и Эллис.
- 4K — ×4–5. Все цифры — оценки; в отчёте этапа — только измерения.

## План проверки
**Прототип (CPU, float64):**
1. M26/M27: попадание в объекты на всех фигурах-носителях (гиперплоскость, S³, эллипсоид, Эллис, M11, M12) —
   точка попадания против эталона DOP853 tol 1e-12 с плотным выводом и поиском корня; критерий: ошибка ≤ C·tol
   и сходимость порядка ≈ 3–4 по tol. Отдельно — скользящие лучи (прицельный параметр → радиус шара).
2. M28: касательность и нормировка ω; pdf Ламберта и GGX интегрируются в 1 (Монте-Карло по полусфере T_xM);
   взаимность BSDF.
3. M29: тест допустимости соединений против перебора (сэмплы отрезков, проверка шаров/объектов по точкам).
4. M32: перенос базиса против решения уравнения на Jet15/HVP и на S³ против аналитики (параллельный перенос
   по большому кругу).
5. Малый трассировщик прототипа: **печь** (альбедо 1, однородный фон L = 1 ⇒ каждый пиксель 1 ± статистика) на
   гиперплоскости, M11, M12, Эллисе; **NEE+MIS = только BSDF** (по пикселям: z-оценки, доля |z| > 4 ≤ 1e-3,
   среднее по кадру в пределах 4σ); **гиперплоскость против независимого евклидова трассировщика** (прямые
   в R³, без кода M — как трюк S¹×R² на этапе 2).

**GPU (float32):**
6. U1 для объектов (g, ∇g) против прототипа.
7. Попадания и точки попадания GPU против прототипа-f32/f64 (критерий DD-004 п. 3: ≤ 4× ошибки прототипа-f32).
8. Трассировщик GPU против эталона прототипа при равных spp (те же статистические критерии), печь на GPU.
9. Развёртка tol_max (M30): смещение против tol_max = 1e-4 при 4096 spp; выбрать наибольший tol_max с
   PSNR смещения ≥ шумового пола 1024 spp. Аналогично c_hit и ε_off (утечки света: замкнутая коробка с источником
   внутри, снаружи должно быть 0).
10. Конусы M31: lod против эталона «много сэмплов без мипов» на сцене с отражением фона в металле.
11. Профиль: 1080p и 4K, 1 spp + денойзер, 64 spp + денойзер; мегаядро против wavefront; время денойзера
    (OptiX и/или OIDN); регистры и занятость, как на этапе 3.

## Риски и открытые вопросы
- **float32 и смещение от поверхности** — классический источник «акне» и утечек; на |x| ≈ 20 ulp ≈ 2e-6.
- **Скользящие лучи у объектов в кривой зоне** — много шагов; потолок n_max и счётчик.
- **Плоские конусы в кривой зоне** — неверный lod у горловины для вторичных лучей (измеряется, п. 10).
- **Границы классов «фон/стохастика»**: ореолы денойзера; флаг «смешанный» должен ловить всё, что попадает
  в след (c_mix подбирается; при глубине резкости след большой).
- **Эллис без плоских зон**: только BSDF-сэмплирование — шумно с малыми источниками; это следствие правила
  задания, не дефект. Фон как источник работает только через BSDF.
- **Регистры**: мегаядро пути (BSDF + интегратор + MIS) может превысить 64–128 регистров — wavefront разделяет.
- **Стоимость HVP на первичном сегменте** (для M32) — измерить; запасные варианты описаны.
- Денойзер: лицензия заголовков OptiX (не в репозиторий), CUDA Toolkit, обмен памятью — вопрос 2.
