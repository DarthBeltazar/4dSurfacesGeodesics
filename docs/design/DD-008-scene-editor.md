# DD-008: GUI и быстрое редактирование сцен
Статус: **Accepted** (принят самостоятельно: ревью пользователя обязательно только для DD-004 и DD-005)
Этап: после 5 (запрос пользователя, журнал 2026-10-24-08)        Дата: 2026-10-24

## Контекст и задача
Запрос: «добавить GUI и возможность быстрого редактирования сцен». Сейчас сцена «запекается»: объекты, материалы и
источники — `static const` в сгенерированном `pt_scene.slang`, многообразие — дефайн `SCENE` с константами в
`scenes.slang`. Любая правка — перегенерация, перекомпиляция шейдеров и перезапуск окна. Окно (DD-007) — SDL3 +
compute, UI нет. Выбор пользователя: **Dear ImGui в окне**; объекты правятся **мгновенно**, многообразие — из GUI
**с перекомпиляцией на лету**.

## Цели / не-цели
**Цели:**
- файл сцены (JSON, `scenes/*.json`): многообразие и параметры, объекты, материалы, стартовая камера;
- данные объектов в буфере GPU, правка без перекомпиляции (положение, размер, материал, излучение,
  добавление/удаление до `PT_MAXOBJ`);
- панели ImGui: сцена, объекты, рендер (экспозиция, денойзер, скорость), сохранение/загрузка JSON;
- смена многообразия или его параметров из GUI: генерация в Python в фоне, перезагрузка графа без закрытия окна,
  камера и объекты проецируются на новое M.

**Не-цели:** произвольные SDF из GUI (только ball4 / torus / plane, как сейчас); новые многообразия (только
параметры имеющихся); правка фона; временная репроекция.

## Математика
**M34 (черн.). Допустимость NEE-источника при правке.** Излучающий 4D-шар (c, r) — NEE-источник, только если сцена с
плоскими зонами, |c_w − w_лист| < 1e-6 для одного из листов и шар целиком в зоне: |c_xyz − cᵢ| ≥ ρ₀ + r для всех
шаров кривизны. Иначе он излучает только через сэмплирование BSDF (MIS-вес BSDF-попадания = 1, `is_light` = false) —
несмещённо, но шумнее. Правило одно в Python (`scenefile.nee_lights`) и в хосте (C++), проверяется равенством строк
буфера; на имеющихся сценах совпадает с заданными вручную списками.

**Привязка к M.** У объекта флаг `on_M`: после правки центр проецируется на M (M3, Ньютон по ∇f; ядро `pt_snap`).
В плоской зоне ∇f ∥ e_w — меняется только w, т. е. объект остаётся на своём листе.

## Предлагаемое решение
1. **Объекты в буфере.** Заголовок `pt_scene.slang` содержит только данные многообразия (плоские зоны) и
   `PT_MAXOBJ = 32`. Объекты — строки float4 в хвосте буфера камеры `gCam[8…]` (он уже привязан на binding 0 во
   всех конвейерах, включая `cam_step`, — привязки не меняются):
   - строка 8: (n_obj, n_light, 0, 0); строки 9–16: индексы NEE-источников (по 4 в строке);
   - объект k, строки 17 + 6k …: центр; (вид, a, b, знак) — ball4 (r), torus (R, r), plane (ось, смещение, знак);
     PL (как раньше); альбедо и вид материала; излучение и шероховатость; (граница, on_M, 0, 0).
   - `obj_g` — `switch` по виду, обобщённая по `IReal` (Real / Dual4 / Jet).
2. **Файл сцены** (`prototype/geo4d/scenefile.py`): `scene_to_json` / `scene_from_json` поверх параметризованных
   `shapes.*`; имеющиеся сцены приложения экспортированы в `scenes/`. `app.py --scene-file`.
3. **Параметры многообразия** — дефайны `scenes.slang` (`MF_B`, `MF_RHO0`, `MF_W`, `MF_C`, `MF_R`, `MF_r`, …)
   со значениями по умолчанию, равными нынешним константам, — старые тесты не меняются. `SCALE` = `Shape.scale`
   той же фигуры (иначе α из ADR-0001 разойдётся с прототипом).
4. **Хост.** ImGui (FetchContent, закреплённая версия; бэкенды SDL3 + Vulkan, volk) поверх кадра: после копии в
   образ swapchain — проход рендеринга ImGui (очередь compute + graphics, образы swapchain с COLOR_ATTACHMENT).
   Ввод камеры не принимается, когда ImGui захватил клавиатуру/мышь. Правка объекта → упаковка строк в C++ →
   запись в буфер `cam` после ожидания кадра → кадр секцией `move` (класс пикселей и режим A зависят от объектов),
   накопление сбрасывается. В режимах замера/дампа (`hidden`, `bench`, `dump`) оверлей выключен.
5. **Перекомпиляция.** Хост сохраняет JSON (с текущей камерой, прочитанной с GPU) и запускает в фоне
   `python app.py --scene-file … --graph-only DIR` (директива графа `rebuild`), окно продолжает рисовать старую
   сцену. По завершении — новый `GraphProgram`, повторный импорт буферов денойзера; при ошибке Python (недопустимые
   параметры) — сообщение в окне, старая сцена остаётся.

## Рассмотренные альтернативы
- Отдельный редактор на Python + IPC — отклонён пользователем.
- Отдельный набор дескрипторов (set 1) под объекты — чище, но правки во всех вызовах `gpu.run` и хосте; хвост
  буфера камеры даёт то же без изменения привязок.
- Параметры многообразия в буфере без перекомпиляции — трогает горячий код SDF; не нужно по выбору пользователя.
- Перезапуск окна при смене многообразия — запасной вариант, если перезагрузка графа в процессе окажется хрупкой.

## Бюджет
Чтение объектов из буфера вместо констант и цикл до рантаймового n могут замедлить ядра (проход камеры — 247
регистров). Критерий: сцена 3, 1080p — не хуже +5 % к 36.3 / 13.9 мс (движение/покой); иначе измерить и решить.

## План проверки
- `-m gpu` без изменений проходит (печь, MIS против «только NEE», сверки с прототипом).
- Круговой обмен JSON для всех сцен приложения: те же строки буфера и тот же заголовок.
- Строки буфера из C++ = строки из Python (директива дампа).
- Горячая правка в сценарии замера (`edit <кадр> <объекты.npy>`) после N кадров покоя = холодный старт с
  отредактированной сценой (тот же seed и число кадров).
- Ненулевые параметры многообразия: GPU против прототипа (критерий ≤ 4× float32).
- Замер времени кадра (бюджет выше).

## Риски
Ресурсы ImGui на очереди compute (нужна graphics); пересоздание денойзера; на Linux fd принадлежит CUDA после импорта.

## Итог реализации
(журнал: docs/log/2026-10-24-08.md; тесты: `tests/test_scene_editor.py`)
- П. 2–5 — по плану. Буфер объектов — хвост буфера камеры; хост проверяет при загрузке, что его упаковка строк
  совпадает с Python (`rows_check`, 0 на исходных сценах).
- **П. 1 изменён по замеру.** Полностью динамические объекты (число и виды тоже из буфера, `switch` в цикле до
  рантаймового n) превысили бюджет: сцена 3, 1080p — 51.9 / 16.6 мс против 36.3 / 13.9 (проход камеры 14.0 → 25.9 мс,
  трассировщик 4.7 → 7.5 мс; регистры те же — 246/247, т. е. потеряна специализация, а не занятость; read-only путь
  чтения ничего не дал). Решение (выбор пользователя): **два варианта шейдеров**.
  - Быстрый (по умолчанию): число объектов, их виды и оси полупространств зашиты в `pt_scene.slang`, параметры —
    из строк; в `pt_sample` строки копируются в groupshared. Правка параметров (положение, размер, материал,
    излучение, «на M») — сразу.
  - **Режим редактирования** (Tab или флажок в панели «Объекты»; включается сам при добавлении/удалении/смене
    формы): граф с динамическими шейдерами (`PT_DYNAMIC 1`, `app_graph_dyn.txt`) — любая правка сразу, кадр
    медленнее (1080p: 52.3 / 16.2 мс; `results/stage-5/2026-10-24_app_bench_two_wormholes_*_editmode`). Выход: если структура
    не менялась — обратно к быстрому графу (смена графа 0.2–0.3 с: буферы, кубмапа, конвейеры, денойзер); иначе
    быстрые шейдеры перегенерируются в фоне (11–18 с на 720p: Python, фон, slangc; `results/stage-5/2026-10-24_editor_regen_time`),
    окно до готовности остаётся в режиме редактирования.
  - Смена графа сохраняет камеру побитово; кадр после смены — секция `edit` с зерном накопления, поэтому цикл
    «вход → структурная правка → выход» побитово равен холодному старту (`test_app_edit_mode_structural_cycle`).
- **Добавлено по ходу:** секция `edit` (кадр со сбросом без шага камеры) и зерно ГСЧ по номеру сэмпла накопления —
  горячая правка побитово равна холодному старту; директивы `edit`, `remanifold`, `ui` для автоматических проверок
  правки, перегенерации и оверлея; при перезагрузке графа директивы сценария переносятся из исходного графа.
- Панели разнесены на два окна («Сцена» слева, «Объекты» справа) — в одно окно 720p не помещалось.
- Время кадра (быстрый граф, сцена 3): 1080p — 37.1 / 14.5 мс, 720p — 17.3 / 7.35 мс (`results/stage-5/2026-10-24_app_bench_two_wormholes_*_editor2`); бюджет +5 % — на границе: 1080p +2 % / +4 %, 720p +6 % / +5 % (движение / покой). **Принято:** разброс
  повторных замеров одного варианта — ±3 % (пять прогонов 1080p в движении: 35.8–38.2 мс, журнал), остаток — сами
  загрузки параметров объектов, цена правки параметров без перекомпиляции.
