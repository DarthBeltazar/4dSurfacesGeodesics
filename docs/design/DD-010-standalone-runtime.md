# DD-010: окно без Python
Статус: **Accepted** (пользователь одобрил, журнал 2026-10-25-02)
Этап: после 5 (самостоятельное приложение, [концепция](concept-standalone-nodes.md))        Дата: 2026-10-25

## Контекст и задача
Цель — самостоятельное приложение, которое легко ставится и запускается на других машинах (сначала Windows, поставка —
zip). Сейчас окно — Python-скрипт `prototype/scripts/app.py`, а хост `geo4d_gpu app <граф>` — исполнитель готового
графа (DD-004, DD-007). При каждом запуске и каждой перегенерации Python:

| что делает Python | где | цена |
|---|---|---|
| читает сцену, строит фигуру, объекты, плоские зоны, мета (`scene_id`, выход, `s_max`, `ell_max`) | `scenefile.build` | импорт JAX ~2–3 с |
| процедурный фон: `bake(background, 512)` + мипы, таблица выборки фона (M29) | `pathtrace.procedural_env`, `env_table` | ~8 с (кэш на диске, DD-009) |
| базис камеры | `camera.make_camera` (jax.grad) | — |
| буфер камеры: камера, константы детектора, строки объектов и многообразия | `gpu_modea.camera_buffer`, `gpu_pt.object_rows/manifold_rows` | — |
| заголовок сцены `pt_scene.slang`, дефайны, push-константы | `gpu_pt.scene_header/_defs/_push` | — |
| компиляция шейдеров | `gpu.compile_shader` → `slangc.exe` процессом на ядро, последовательно | 3.6–3.8 с без кэша (`probe_compile`) |
| граф кадра (буферы, конвейеры, секции, директивы) | `gpu_pt.app_graph` | — |
| перегенерация (разрешение, структура объектов, многообразие при выходе из режима редактирования) | хост запускает `app.py --graph-only` | 2.3 с (разрешение), 9.0–9.4 с (структура) |

Поэтому релиз v0.1.0-alpha требует Python 3.12 и ~1.5 ГБ `.venv` (JAX, SciPy, Matplotlib), а смена разрешения и
структуры идёт секундами. Часть уже продублирована в C++ ради мгновенной правки (DD-008/DD-009): строки объектов
(`rows_check`), строки многообразия и правило параметров (`editor.cpp::manifold_info`, `mf_check`), касательный базис
(`tangent_basis`), разбор JSON формата `scenefile.save` (`read_scene_json`).

Нодовая система (DD-011) будет генерировать шейдеры из графа, и делать это должен уже C++. Поэтому сначала этот DD:
перенести запуск окна в хост **без изменения того, что рисуется** (те же шейдеры, те же числа), а потом наращивать.

## Цели / не-цели
**Цели:**
- `geo4d_gpu` открывает окно сам: `geo4d_gpu [сцена.json] [--res WxH] [--fullscreen] [--vsync] …`; без аргументов —
  сцена по умолчанию. Python, JAX, `slangc.exe` и Vulkan SDK на машине пользователя не нужны.
- В C++ (владелец — хост): модель сцены и её JSON; фигуры и их мета; фон и таблица выборки; буфер камеры; заголовок,
  дефайны и push-константы; построение графа кадра; компиляция шейдеров через Slang API с кэшем на диске.
- Смена разрешения — без перегенерации в Python (пересоздание буферов в процессе); структурная перегенерация —
  компиляция в фоновом потоке, ядра параллельно.
- Пользовательские каталоги: кэш SPIR-V и `VkPipelineCache` — `%LOCALAPPDATA%\geo4d\cache`, настройки и компоновка
  ImGui — `%APPDATA%\geo4d`; каталог программы только для чтения (шейдеры-исходники, сцены).
- Кадры побитово равны нынешнему окну при том же фоне (см. «План проверки»).

**Не-цели:**
- нодовая система, режим предпросмотра, наложения, новая компоновка окна — DD-011;
- zip и проверка на чистой машине — DD-012;
- изменения в шейдерах и численных методах (кроме того, что нужно для запуска без Python);
- перенос прототипа и тестов: Python остаётся эталоном и средой тестов; режимы `run`/`graph`/`denoise` хоста
  не меняются.

## Математика
Новых формул нет. Переносятся без изменений: M3 (проекция камеры на M), касательный базис `make_camera`
(уже в C++, DD-009), правило NEE-источников M34 (уже в C++), M29 (таблица выборки фона: тексель ∝ яркость ·
телесный угол на уровне n = 32). Фон — `render.background` (не формула из math.md, а процедурная картинка): градиент
по широте, сетка 15°, цветные полюса.

## Предлагаемое решение
### 1. Модель сцены (`gpu/src/scene.{hpp,cpp}`)
- `Scene`: многообразие (вид, параметры), фон (`procedural` | `none`), объекты (вид, параметры, материал, `on_M`, имя),
  камера (x, f, up, right, fov), скорость. Чтение и запись формата `scenefile.save` (version 1) — JSON-библиотека
  nlohmann/json (FetchContent, закреплённая версия, header-only); самодельный `read_scene_json` удаляется.
- Каталог фигур: вид → (scene_id, SCALE = `Shape.scale`, выход, плоские зоны, `s_max`, `ell_max`, параметры по
  умолчанию, проверка параметров). Это расширение нынешнего `manifold_info` (там уже есть SCALE, плоские зоны и
  `check_params`): один источник для строк многообразия, заголовка и дефайнов.
- Проекция `on_M`-центров и точки камеры на M (M3) — на CPU, по `sdf<Real>`-эквиваленту фигуры в C++ с градиентом
  дуальными числами (4 направления). Для фигур каталога это 8 коротких формул (`scenes.slang`); вариант «через
  `pt_snap` на GPU» уже работает в режиме редактирования и остаётся там.

### 2. Кодген (`gpu/src/codegen.{hpp,cpp}`)
- `scene_header(scene, dynamic)` — порт `gpu_pt.scene_header` (заголовок `pt_scene.slang`: плоские зоны, `PT_NOBJ`,
  `obj_g` по объектам); `defines(scene, nj, dynamic)` — порт `_defs` + `manifold_defines`; `push(scene, params, …)` —
  порт `_push` (структура `PTParams` один к одному).
- Буфер камеры — порт `camera_buffer` (8 строк: камера, tf/W/H/focus, апертура/σ_pix/k_grad, θ_pix и пороги
  детектора `Detector()`, режим фильтра и размер грани) + имеющиеся упаковки объектов и многообразия.
- Числа печатаются как в Python (`%.9g`) — заголовки совпадают байт в байт, значит и SPIR-V.

### 3. Компиляция шейдеров (`gpu/src/shader_compiler.{hpp,cpp}`)
- Slang API (`slang.lib`/`slang.dll` из Vulkan SDK 1.4.328.1 — та же версия 2025.17.2, что у `slangc.exe`): один
  `IGlobalSession` на процесс (загрузка базового модуля — один раз), сессия с целью `spirv_1_6`, `-O2`,
  `-fvk-use-entrypoint-name`, путями поиска `shaders/` и каталога заголовка; дефайны — макросы сессии.
- Кэш SPIR-V на диске с тем же ключом, что у Python (sha256 всех `.slang`, исходник, вход, дефайны, файлы include),
  в `%LOCALAPPDATA%\geo4d\cache\spv`. Тесты по-прежнему используют свой кэш `gpu/build/spv`.
- Параллельность: ядра графа — задачи пула потоков. Потокобезопасность Slang: `IGlobalSession` не потокобезопасен,
  поэтому на поток — своя сессия от одного глобального, если API это допускает; иначе — по глобальной сессии на
  поток (базовый модуль грузится N раз, ~0.1 с каждая) — **замерить и выбрать** (риск 1).
- `VkPipelineCache` сохраняется на диск при выходе и загружается при старте (повторная сборка конвейеров — 2 мс
  против 0.74 с при промахе, `probe_compile`).

### 4. Фон (`gpu/src/environment.{hpp,cpp}`)
- Порт `render.background` на C++ (CPU, параллельно по граням): уровень 0 кубмапы (2 листа × 6 граней × 512² RGB,
  float32, без рамки — то, что сейчас `cube_for_gpu(mips[0])`). Мипы и BC6H — как сейчас, на GPU в хосте.
- Таблица выборки фона (M29, `env_table`): уровень n = 32 — среднее блоков 16×16 уровня 0 (внутренность мипа
  Python — повторный бокс 2×2, рамка в таблицу не входит), затем pmf ∝ яркость · телесный угол и cdf.
- Фон `none` — нули и равномерная таблица (как `constant_env(0)`).
- GPU-версия фона — в DD-011, когда фон станет нодой «Окружение».

### 5. Граф кадра без текстового файла (`gpu/src/frame_graph.{hpp,cpp}`)
- Порт `gpu_pt.app_graph`: те же буферы, конвейеры, push-строки и секции (`move`, `edit`, `move_nobg`, `edit_nobg`,
  `snap`, `static`, `post`) и директивы приложения — но в виде структуры для `GraphProgram`, без записи файла и без
  `.npy` на диске (буферы заполняются из памяти). Для отладки и тестов — `--dump-graph DIR` пишет текстовый граф и
  `.npy` в формате, который понимает `geo4d_gpu app <граф>`.
- Перегенерации в процессе:
  - разрешение — новый граф с теми же SPIR-V (ядра от разрешения не зависят), буферы и денойзер заново;
  - структура объектов и многообразие при выходе из режима редактирования — кодген + компиляция в фоновом потоке,
    окно рисует старый граф (как сейчас с Python), затем смена графа с той же камерой (имеющийся путь DD-008/009).
- Директивы сценария замера (`bench`, `dump`, `edit`, `remanifold`, `loadscene`, `resize`, `editmode`, `mouse`,
  `record`, `window`, `ui`, `hidden`) — флаги командной строки и файл сценария; `app.py` становится тонкой обёрткой,
  которая запускает `geo4d_gpu` с этими флагами (для имеющихся тестов и `--bench`).
- `geo4d_gpu app <граф.txt>` остаётся (отладка в CLion, тесты переходного периода).

### 6. Каталоги и ошибки
- Ресурсы ищутся относительно exe: `shaders/`, `scenes/`; переопределение — `GEO4D_ROOT` (запуск из дерева
  разработки).
- Ошибки, которые раньше ловил Python (недопустимые параметры, ошибка компиляции), — сообщение в окне и в журнале
  `%APPDATA%\geo4d\log.txt`; старая сцена остаётся.

### Порядок реализации (каждый шаг — с проверкой)
1. `scene` + `codegen` + `environment` и команда `geo4d_gpu export-graph <сцена> <DIR>` (тот же граф, что
   `app.py --graph-only`) — сверка с Python без окна.
2. `shader_compiler` — SPIR-V из API = SPIR-V из `slangc.exe` для всех ядер всех сцен; замер холодной сборки.
3. Окно на графе из памяти: `geo4d_gpu [сцена]`; смена разрешения в процессе; `VkPipelineCache` на диске.
4. Перегенерация структуры в фоновом потоке; `app.py` — обёртка; перевод тестов окна.
5. Удаление Python-путей перегенерации (`rebuild`, `RebuildKind` через процесс), обновление README и `ide_configs.py`.

## Рассмотренные альтернативы и почему отвергнуты
- **Встроенный Python** (embeddable Python + JAX в zip): ~1.5 ГБ, импорт JAX секунды при каждой перегенерации, хрупкие
  колёса numpy/jaxlib под разные машины. Не «легко ставится».
- **Заморозка в exe** (PyInstaller/Nuitka с JAX): тот же размер, плюс известные проблемы с jaxlib/XLA при заморозке;
  перегенерация всё равно через Python.
- **`slangc.exe` процессами** (как сейчас, но из C++): проще, но 0.14 с на процесс и повторный разбор
  `pathtrace.slang` на каждое ядро (`probe_compile`: последовательно 3.8 с, параллельно 1.8 с); API даёт общий
  базовый модуль и кэш модулей. Остаётся запасным вариантом, если API окажется непотокобезопасным (риск 1).
- **Поставлять запечённый фон файлом** (сегодняшний кэш `.npz`): проще всего, но фон станет нодой (DD-011) и должен
  строиться в программе; порт на C++ — ~60 строк.
- **Фон сразу на GPU**: правильная цель для DD-011; для переноса без изменений CPU-порт проще сверять с Python.
- **Держать Python как владельца кодгена, C++ только зеркало** (как DD-008/009): для самостоятельного приложения
  невозможно; после DD-010 владелец — C++, Python — эталон в тестах.

## Бюджет производительности и памяти
- Кадр — без изменений (те же SPIR-V): сцена 3, 1080p, быстрый граф 37.1 / 14.5 мс, режим редактирования
  58.5 / 18.2 мс (±3 % — разброс повторных замеров).
- Холодный старт (пустые кэши): цель ≤ 5 с (фон на CPU — оценка ≤ 0.3 с, компиляция параллельно ~2 с, конвейеры
  ~0.8 с); тёплый (кэши SPIR-V и конвейеров) — ≤ 1 с. Сейчас: импорт JAX + кэш фона + компиляция — 10+ с.
- Смена разрешения: цель ≤ 0.5 с (было 2.3 с через Python).
- Структурная перегенерация: цель ≤ 3 с (было 9.0–9.4 с).
- Размер: `slang.dll` 17.6 МБ + `slang-glslang.dll` 6.8 МБ (если нужен для −O2) + `slang-glsl-module.dll` 1.3 МБ
  уже лежат в релизном zip (там же `slangc.exe`, он больше не нужен); минус `.venv` ~1.5 ГБ.

- Замеры: холодный/тёплый старт, смена разрешения, структурная перегенерация, кадр (`--bench`) — в

## Риски и открытые вопросы
1. **Потокобезопасность Slang API** — от неё зависит параллельная компиляция. Запасной вариант — пул процессов
   `slangc` (тогда `slangc.exe` остаётся в поставке).
2. **SPIR-V из API ≠ из `slangc.exe`** (другие опции по умолчанию) — сравнить опции, иначе принять равенство кадров.
3. **−O2 требует `slang-glslang.dll`** (spirv-opt) — проверить, какие DLL реально нужны.
4. **Объём переноса тестов окна** (20 тестов на сценарии и директивы) — обёртка `app.py` сохраняет их интерфейс.
5. **Проекция на M в C++** для `on_M` и камеры должна совпасть с `shapes.project_points` (Ньютон, 30 итераций,
   float64) — иначе строки разойдутся в младших битах; критерий — побитовое равенство после округления до float32.
6. **Пути не ASCII в Windows** (имя пользователя или каталог по-русски — обычное дело у целевых пользователей):
   `load_scene(std::string)`, `npy_read/npy_write`, узкий `argv` идут через кодовую страницу ANSI; `from_u8(argv)`
   неверно декодирует кириллицу. До шага 3 — `fs::path` насквозь и широкий argv (или манифест приложения с
   `activeCodePage` UTF-8); тест — каталог с кириллицей в имени.
7. **Две упаковки строк**: редактор (`editor.cpp`: `pack_rows`, `manifold_info` во float) и новый кодген (double).
   На шаге 3 редактор должен упаковывать через `codegen::object_rows/manifold_rows`, иначе горячая правка и
   холодный старт разойдутся в младших битах (тесты «правка = холодный старт» побитовые).
8. `default_dirs` ищет корень как «exe → три уровня вверх» (дерево разработки); для zip — `shaders/` и `scenes/`
   рядом с exe (п. 6 решения).

## Итог реализации
**Шаг 1 — сделан** (`scene.{hpp,cpp}`, `environment.{hpp,cpp}`, `codegen.{hpp,cpp}`, `sha256.hpp`,
`export_graph.cpp`; тест `tests/test_standalone_export.py`, 11 passed):
- `geo4d_gpu export-graph <сцена> <каталог> [--res] [--cube] [--fov] [--vsync] [--fullscreen]` пишет те же
  `app_graph.txt` / `app_graph_dyn.txt` и `.npy`, что `app.py --graph-only`, без Python.
- Текст графов совпадает построчно для всех 7 сцен (кроме директивы `rebuild`). В том числе пути SPIR-V: ключ кэша
  `compile_shader` (sha256 исходников, заголовка и `json.dumps` дефайнов) воспроизведён байт в байт.
- Кубмапа фона и таблица выборки (M29) — **побитово** равны JAX/numpy: порядок float32-бокса мипов и попарное
  суммирование numpy повторены. Буфер камеры — побитово, кроме базиса камеры f, r, u: порядок суммирования
  скалярных произведений в Грам–Шмидте (numpy против C++) и дополнение r из SVD против координатной оси дают шум
  ≤ 1e-15 и знак нуля в почти нулевых компонентах.
- Кроме 7 сцен — 3 синтетические (`on_M`-центры в зоне кривизны и на торе, нестандартные параметры многообразий,
  NEE-допустимый, в зоне и вне листа излучатели, пробелы в путях): всё так же совпадает, кадр — побитово.
- Кадры из графа C++ и графа Python на GPU — побитово равны (`test_export_renders_same`: две горловины, S³, Эллис).
- Особенности Python, повторённые ради совпадения: заголовок `pt_scene.slang` пишется с CRLF (Path.write_text в
  Windows; входит в ключ кэша), граф режима редактирования — без `vsync`/`fullscreen`.
- Модель сцены — в double (как Python), во float32 — только при упаковке; `editor.cpp` пока не переведён на неё
  (шаги 3–4).
