# 2026-10-25-02: обсуждение нодовой системы и самостоятельного приложения

Запрос пользователя: «Давай продумаем, как будет работать нодовая система с точки зрения пользователя, какие будут
ноды и т.д.». Код не писали — только проектирование. Итог — [concept-standalone-nodes.md](../design/concept-standalone-nodes.md).

## Ход обсуждения
1. Предложены три контекста графа (многообразие f, объекты g, материалы) вместо одного «графа SDF»: у f и g разные
   требования (гладкость и метаданные `hcap`/плоские зоны/выход у f; липшицевость у g). Свободная CSG над f отвергнута:
   из выражения нельзя вывести `hcap`, а две горловины — это сложение профилей, а не smin.
2. Пользователь выбрал ноды выражений, мгновенный режим редактирования с перекомпиляцией на выходе, прикрепляемую
   панель нод, процедурные текстуры; подграфы — позже, но с заделом. Следствие: в режиме редактирования граф должен
   исполняться интерпретатором байткода (`switch` по заранее известным видам, как в DD-008/009, не годится для
   произвольных выражений). Риск — скорость (регистры Jet15), отсюда проба до DD.
3. Пользователь уточнил: это самостоятельное приложение, которое должно легко ставиться на другие машины. Вывод:
   в работающем приложении не должно быть Python (сейчас он строит граф кадра, генерирует шейдеры, строит фон в JAX
   и вызывает slangc). Кодген графа нод поэтому сразу пишется на C++, а Python остаётся эталоном в тестах; библиотека
   нод — данные на языке выражений, общем для C++ и Python.
4. Решения: сначала Windows, проверка только на этой машине, поставка — zip, излучение по текстуре не в v1, проба
   интерпретатора — до DD.

## Пересмотрено по ходу
- В первом ответе предлагалось оставить кодген в Python (хост только вызывает rebuild, как в DD-008). После
  требования «самостоятельное приложение» это отменено: иначе кодген пришлось бы переписывать.
- В DD-008 «произвольные SDF из GUI» были не-целью; нодовая система это отменяет.
- В DD-009 JSON-библиотека была отклонена (8 ключей); для графа нод с подграфами она нужна.

## Проба интерпретатора (по решению пользователя — до DD)
Коммит 8014773. Таблицы и вывод — [concept-standalone-nodes.md, п. 3](../design/concept-standalone-nodes.md).

Сделано:
- `geo4d.bytecode`: программа в SSA, распределение регистров по времени жизни, эталон `evaluate` на jet.ops;
  программы для двух горловин (45 инструкций, 8 регистров) и S³ (9). На CPU побитово = формуле фигуры (f, ∇f, H).
- `scenes.slang`, `MF_PROG`: интерпретатор в режиме редактирования (`SCENE_DYNAMIC`), программа в хвосте буфера
  камеры с `MF_BASE + 7` (хост пишет только строки до `MF_BASE + 7`, хвост сохраняется); `app.py --probe-interp NREG`.
- `prog_u1.slang`, `tests/test_gpu_prog.py`: точность интерпретатора = точности нативного кода.
- `probe_compile.py`: slangc по ядрам (−O0/−O1/−O2, последовательно и параллельно), сборка конвейеров драйвером
  (`GEO4D_PIPE_TIME` в хосте), `GEO4D_SLANG_OPT` в `gpu.compile_shader` (по умолчанию −O2, кэш прежний).
- `-m gpu`: 58 passed (55 + новые).

Что не получилось и почему:
- Первый вариант (switch на 20 операций над jet-числами, не закоммичен): 720p 695 / 173 мс против ~30 / 9.
  `PROG_NREG` 8 или 16 — без разницы.
- Четыре пути над jet (скалярный расчёт g0, g1, g2 по op, затем один `unary`): −15…20 %, но всё ещё 592 / 144 мс
  ([interp](../../results/stage-5/2026-10-25_app_bench_two_wormholes_1280x720_probe_interp)).
- Программа константами в шейдере: −5 % — дело не в чтении инструкций
  ([const](../../results/stage-5/2026-10-25_app_bench_two_wormholes_1280x720_probe_interp_const)).
- Регистры без динамического индекса (развёрнутый выбор): хуже, 1045 / 232 мс
  ([static](../../results/stage-5/2026-10-25_app_bench_two_wormholes_1280x720_probe_interp_static)).
- S³ (9 инструкций): 20.7 → 304 мс — цена почти не зависит от длины программы, суперинструкции не спасут.
- Причина — локальная память под jet-регистры: 2816 байт на поток (`prog_u1`) против 0 (`jets_u1`), регистров 64
  против 56 (статистика конвейера драйвера).
- Перекомпиляция ([probe_compile](../../results/stage-5/2026-10-25_probe_compile)): −O0 ускоряет slangc, но драйвер собирает дольше (1.98 с против
  0.74) и кадр медленнее на 18 % ([−O0](../../results/stage-5/2026-10-25_app_bench_two_wormholes_1280x720_probe_opt-O0) против
  [−O2](../../results/stage-5/2026-10-25_app_bench_two_wormholes_1280x720_probe_opt-O2)). Оценка задержки структурной правки — ~2 с.

## Проба режима предпросмотра (предложение пользователя)
Коммиты «[probe/preview] …». Ядро `pt_preview` в `pathtrace.slang`, замер `probe_preview.py` →
[probe_preview](../../results/stage-5/2026-10-25_probe_preview); таблица — в concept, п. 3.
- Две горловины, 720p: нативно 1.47 мс, интерпретатор 55.4 мс; 640×360 — 0.52 / 17.3 мс.
- S³: лучи без попаданий идут до s_max = 8πR (пурпурные пиксели на [кадре](../../results/stage-5/2026-10-25_probe_preview/S3_1280x720_native.png)) — это почти
  всё время; предел в один оборот (2πR) — в 3.8–4.1 раза быстрее (720p: интерпретатор 44 мс).
- Отношение интерпретатор/нативно в предпросмотре хуже, чем в полном кадре (×33–41 у горловин): нативное ядро очень
  лёгкое. Но в абсолюте интерпретатор в предпросмотре — 18–60 кадров/с.
- Нативная сборка маленького `pt_preview` всё равно ~1.3 с (slangc −O2 1.11 с — фронтенд всего `pathtrace.slang`;
  −O0 быстрее в slangc, но драйвер дольше) — мгновенным предпросмотр делает только интерпретатор.

## Решения пользователя после проб
- Схема «предпросмотр на интерпретаторе сразу, нативная компиляция в фоне» — принята.
- Наложения — настраиваемые и во всех режимах. Решение: G-буфер центрального луча (в рендере его пишет проход
  камеры, в компактных пространствах — проход предпросмотра), смешивание после тонмаппинга.
- Компоновка: основной вьюпорт в центре, кнопка настроек в правом верхнем углу, остальные меню пристёгиваются к его
  сторонам. Детали — concept, п. 4.

## DD-010, шаг 1 (пользователь одобрил DD — Accepted)
- C++: модель сцены в double (`scene`), фон и таблица выборки (`environment`), кодген и граф окна (`codegen`),
  `sha256.hpp`, команда `geo4d_gpu export-graph`; nlohmann/json 3.11.3 (FetchContent, zip с хэшем).
- `tests/test_standalone_export.py`: графы всех сцен совпадают с `app.py --graph-only`, кубмапа и таблица фона
  побитово, кадры на GPU побитово.
- Что пришлось повторить из Python ради совпадения: CRLF в заголовке (входит в ключ кэша SPIR-V), отсутствие
  `vsync`/`fullscreen` в графе режима редактирования, попарная сумма numpy в нормировке таблицы фона.
- Не совпадает (принято): базис камеры f, r, u — шум ≤ 1e-15 и знак нуля (порядок суммирования в Грам–Шмидте,
  SVD против оси). Синтетические сцены (on_M, нестандартные параметры, края M34, пробелы в путях) — совпадают.
- Риски шага 3 записаны в DD-010: пути с кириллицей (ANSI в argv/ofstream), две упаковки строк (редактор во float
  против кодгена в double), корень по exe для zip.

## DD-010, шаг 2
- `shader_compiler`: Slang API в режиме командной строки, глобальная сессия на поток, долгие ядра первыми;
  `export-graph --compile`. SPIR-V побитово = `slangc.exe` (`test_compile_matches_slangc`).
- Не сработало: `getEntryPointCodeBlob` в режиме командной строки — падение; без `setCommandLineCompilerMode` не

- Сборка 27 ядер обоих графов при пустом кэше: 8 потоков — 2.5 с (1 поток — 9.7 с), предел — `pt_sample`
  ([standalone_compile](../../results/stage-5/2026-10-25_standalone_compile)).

## DD-010, шаг 3
- `geo4d_gpu [сцена.json] …` — окно без Python: граф в памяти (`memfs`), шейдеры в процессе, перегенерации
  редактора — `RebuildFn` в потоке; манифест UTF-8; `VkPipelineCache` на диске; `--extra` для сценариев.
- Тесты `test_standalone_window.py` (6) — побитовые сверки с Python-путём и холодным стартом; `-m gpu` — 68 passed.
- Замер ([standalone_startup](../../results/stage-5/2026-10-25_standalone_startup)): тёплый старт 0.75 с (Python 2.9 с), холодный 4.2 с, смена разрешения 0.21 с
  (было 2.3 с), структурная перегенерация 2.0 с (было 9.0–9.4 с).
- Риск 7 (две упаковки строк) на деле — уже существовавший `rows_check`: после перегенерации из JSON с числами
  float 7.95e-8 (тот же эффект был и у Python); побитовые тесты «правка = холодный старт» проходят. Свести упаковку к
  `codegen` — шаг 5.
